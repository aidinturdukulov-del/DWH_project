# Оптимизация самого тяжёлого запроса: расчёт `loan_snapshot_daily`

Самый тяжёлый запрос решения — полный расчёт ежедневных снимков: 1 561 кредит,
522 182 строки (кредит × день с даты выдачи по 01.11.2026).

| | Время выполнения | Файл плана |
|---|---|---|
| До | **5 862 мс** (≈ 4 900 мс без JIT) | [explain/before.txt](explain/before.txt), запрос — [explain/before_query.sql](explain/before_query.sql) |
| После, JIT включён | 1 240 мс | [explain/after_jit_on.txt](explain/after_jit_on.txt) |
| После, `jit = off` (как в модели) | **814 мс** | [explain/after.txt](explain/after.txt), запрос — [explain/after_query.sql](explain/after_query.sql) |

Результат стал быстрее в ~7 раз и **совпадает построчно** со старым расчётом
(`EXCEPT` в обе стороны даёт 0 строк). Postgres 16, `work_mem` по умолчанию (4 МБ),
`EXPLAIN (ANALYZE, BUFFERS)`, замеры повторены дважды.

## Что было не так в исходной версии

Старый запрос строил календарь «кредит × день» (522 тыс. строк) и для каждой строки
считал накопленную сумму плана так:

```sql
due_on_date as (
    select c.loan_id, c.snapshot_date, coalesce(max(s.cum_due), 0)
    from calendar c
    left join sched_cum s on c.loan_id = s.loan_id and s.due_date <= c.snapshot_date
    group by c.loan_id, c.snapshot_date
)
```

В плане это видно по узлам:

* `Merge Left Join ... rows=3 239 243` — неравенство `due_date <= snapshot_date`
  размножает каждый день на все прошедшие плановые платежи: 522 тыс. → 3,2 млн строк;
* `HashAggregate` поверх них — ~1,4 с, чтобы снова сжать до 522 тыс.;
* три сортировки календаря по 0,5 млн строк, все с `Sort Method: external merge Disk: 11–18 МБ` —
  календарь участвует в трёх CTE (`calendar_with_payments`, `due_on_date`, финальное соединение),
  и каждое требует своей сортировки и merge join;
* ещё одно соединение по диапазону (`cum_paid >= prev_cum_due and cum_paid < cum_due`)
  для поиска непогашенного платежа — снова на уровне каждого дня.

Итого: работа пропорциональна «дни × плановые платежи», а не «дни».

## Что изменено

Ключевое наблюдение: **состояние кредита меняется только в дни событий** —
выдача, плановая дата, фактический платёж. Между событиями остаток, просрочка и
первый непогашенный платёж постоянны, меняется только счётчик дней.

Новый расчёт ([dm_loan_snapshot_daily.sql](../dbt_project/models/marts/dm_loan_snapshot_daily.sql)):

1. `events` — объединение выдач, графика и платежей, сгруппированное по (кредит, дата):
   **25 325 строк** вместо 522 тыс.
2. `event_state` — накопленный план и факт оконными `sum() over (... rows unbounded preceding)`
   и `lead()` для границы интервала. Одна сортировка 25 тыс. строк в памяти.
3. `event_state_fifo` — первый непогашенный платёж (`min(due_date) where cum_due > cum_paid`)
   через `LATERAL` с поиском по первичному ключу `raw.schedule (loan_id, due_date)`:
   25 тыс. обращений по 0,013 мс.
4. `generate_series(event_date, next_event_date - 1)` разворачивает интервал в дни
   уже с готовыми значениями: дорогих операций на 522 тыс. строк больше нет,
   только вывод.

Дополнительно — `set jit = off` в `pre_hook` модели. `generate_series` планировщик
оценивает в 1 000 строк, поэтому весь план «видит» ~9,5 млн строк и включает
JIT-компиляцию с инлайнингом и оптимизацией (≈ 440 мс в `after_jit_on.txt`).
На реальных 0,5 млн строк компиляция не окупается: без JIT запрос идёт 814 мс вместо 1 240 мс.

## Почему это важно и для инкремента

Тот же подход делает дешёвым дневной инкремент: события пересчитываются для всех
кредитов (это 25 тыс. строк), а разворачиваются в дни только хвосты, начиная с
`recalc_from` (новые даты + даты опоздавших платежей). Догрузка шага 2 вставляет
49 082 строки вместо пересоздания 522 тыс.; повторный запуск без новых данных —
0 строк за ~0,5 с.

## Чтение «портфеля на дату»

`dm.v_portfolio_on_date` — обычное представление с `group by snapshot_date`.
Фильтр `where snapshot_date = ...` Postgres опускает ниже агрегации, и он идёт по
уникальному индексу `(snapshot_date, loan_id)`:
`Bitmap Index Scan ... Index Cond: (snapshot_date = '2026-06-30')`, ~20 мс на дату.
